# BehaviorGate v3.5.19

**本版重点：让记录说清「做了什么」，让 G3 的归属与证据判断更接近事实，让 G5 按风险对象校准，并把与门无关的编程习惯移出默认注入。**

BehaviorGate 是 Claude Code 的开发行为约束插件，提供子代理预算、完成声明检查、危险模式检查及询问与测试约束。v3.5.19 依据 2026-10-26 的《行为门实际审查与修正方案》收敛修改。它不是安全边界，也不承诺替代代码与业务验收。

- `SHA256SUMS.txt`：发行资产的 SHA-256 校验和。

## 修复

### 1. 记录能准确回答「做了什么」

事件记录新增 `tool_use_id`（关联一次工具调用的开始与结束）、`hook_event`、`elapsed_ms`（本进程耗时）。判定词汇统一为 `deny`（策略拒绝）、`stop_feedback`（收尾打回）、`warn`（可见警告但未拦截）、`inactive`（本轮未生效）、`review_*`（评审自身的调用结果）。

G5 的警告、G6 的重复与用量提醒、配置规则被跳过，现在都会写事件 —— 修前只写 stderr，事后统计只能看到普通工具调用。

非阻断提醒改经宿主支持的字段输出：模型侧用 `hookSpecificOutput.additionalContext`，用户侧用顶层 `systemMessage`。普通放行保持安静，不输出 `permissionDecision: allow`，也不改写原有权限流程。事件里的 `delivery_channel` 只表示「登记到了哪个输出通道」，不表示宿主已接收或模型已采纳。

边界：纯放行不记录；宿主侧超时把进程杀掉时，进程内无法留下事件。这两点已在 `_lib.record_gate_event` 的文档里写明。

### 2. G3 的声明归属与证据关系

- 明确指向更早结果的句子（`10/25 …`、`上一轮 …`、`RESULTS 已记录 …`）不再被当成本轮声明去要证据。判据要求历史标记出现在完成词之前，并被「现在 / 现已 / 目前 / 本轮 / 刚刚」等当前语态否决。
- 语义评审返回「归属不确定」时先提醒，不据此指控完成。
- 普通表达里的具体观测（HTTP 状态码、exit code、监听端口）在中/低风险下不必改写成固定模板；但它必须与本会话【真实的成功工具结果】对上才算证据。只写在正文里、没有任何工具结果可对照的，不作为证据；高风险仍要求完整证据块。

### 3. 绿灯来自实际结果（只读）

新增 `result_scan.py`：只读 transcript 尾部，确认本会话是否真的产生过工具结果，并抽取可核对的观测。

- 证据块声明 L2/L3，但整个会话没有任何工具结果 → 打回，提示补真实验证或降级说法。
- 声明里的具体观测在【成功结果】里找到对应，且那条结果之后没有写操作 → 记 `verified_by_observed_results`。
- 有结果但观测无法与声明对齐 → 放行，但记 `allow_unconfirmed` 并提醒「本轮不作为已验证」。
- 结果之后还有写操作 → 记为过期（`results_superseded_by_later_edit`），不记已验证。
- 只有失败结果 → 不支撑「通过」；只有声明本身是「已复现 / 预期失败」时，失败结果才支撑该具体结论。
- transcript 已截断 → 记为未确认，既不当成「没有证据」打回，也不当成通过。
- 用户已豁免验证 → 允许交付，但明确不是「已验证通过」。
- 读不到 transcript → 如实说明未对照，不据此指控。

边界：这不校验真伪，也不判断观测是否属于同一个对象/操作，只建立「声明 ↔ 已发生结果」的字面对应关系。扫描有界（512 KB / 800 行 / 40 条结果）。

### 4. G7 的条件、范围与授权更新

G7 状态从两个布尔值升级为结构化约束：原话、对象、条件、适用阶段、来源、状态、被替代记录。局部禁令（如「不运行会写数据的测试」）不再被压成全面禁令；新授权只替代对应维度的旧约束。

评审失败时列出「未重新确认」的具体对象与条件；带条件的测试禁令只有在命令出现明确写标志（`--write` / `--fix` / `--updateSnapshot` / jest·vitest `-u`）时才硬拦，其余情况给出可见警告，并说明 fixtures / conftest 仍可能写数据。

### 5. 重复判断

G6 判重改为完整规范化命令的 SHA-256 摘要（前缀只用于显示）。修前按前 200 字符比较，把开头相同、全文不同的多条查询合并成「同一条命令」。

### 6. G5 按风险对象校准

- 读写性质分三态：明确写 → 告警；已确认只读（`select` / `ls` / `file`）→ 不告警；读不出内容（`< seed.sql`、脚本内部、`cat … | sqlite3`）→ 仍按原规则告警，并标明「读写性质未能确定」。
- `cat/tee/printf/echo` 的 heredoc 正文按「写入内容」检查（行锚定），不再整体按命令检查；正文被管道给 `sh`/`bash`/`python` 时仍按命令处理。
- 拦截文案新增「本次检查了什么 / 没有检查什么」：变量展开后的目标、Python/Node 脚本内部逻辑、跨语言等价写法都不在静态检查范围内，真正的边界是沙箱与系统权限。

### 7. 移出与门无关的编程习惯

`protocol_card`（任务合同、逐项闭环、收尾三报）默认关闭，需要的人可自行打开。每次注入仍保留一行事实陈述：程序实际检查的只有 G1 / G3 / G5 / G7。

策略里补充 G1 的语义说明：它是独立资源预算，`agent_spawns = 0` 是成本/范围选择，不是质量保证。

## 已知限制

- G3 仍然无法校验证据真伪，也不能把一项观测推广到全系统。
- G5 无法静态判断任意脚本；换一种语言表达同一意图不会被拦住，也不会因此变安全。
- G7 在工具调用前不做语义判断：带条件的禁问只能提醒，带条件的禁测只能按静态写入标志近似。
- 提醒「已输出到宿主支持的字段」不等于宿主已接收，更不等于模型已纠正；本版未做这三层的实测区分。
- 语义评审的可靠性依赖所配置的模型通道；评审失败时的行为已在上文逐项说明。
- 本版没有做性能基准；不承诺提速百分比，也不承诺修后零误报。
